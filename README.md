# Звёздная одиссея · Репетиции

A self-hosted rehearsal site for the 14th Traditional Ball of РТУ МИРЭА «Звёздная Одиссея» (2026). Open a dance on your phone, scrub with timeline previews, loop a figure at 0.75×, and save a private note at that exact second.

- **Backend:** Go (`cmd/bal`). One binary handles media import and preparation (FFmpeg) and the HTTP server: JSON API, Google and email sign-in, the built SPA, and Range-capable MP4 via `http.FileServer`. Data is in SQLite (pure Go, no CGO).
- **Frontend:** React + TypeScript + Vite, Tailwind v4, shadcn/ui-style components (Radix), Vidstack player.
- **Design:** see [docs/design-brief.md](docs/design-brief.md).
- **Media inventory:** see [docs/assets.md](docs/assets.md), generated by `bal report`.

## Layout

```
cmd/bal/              CLI: import · contact · prepare · report · serve
internal/content/     source record + per-dance media metadata
internal/prepare/     FFmpeg pipeline
internal/store/       SQLite: users, accounts, sessions, notes, marks, progress, reactions
internal/auth/        Google OpenID Connect (PKCE), ID-token verification, passwords
internal/server/      HTTP: API, OAuth callback, /media, SPA
web/                  React app (built to web/dist)
content/sources.json  hand-checked source record: exact posts, original filenames, cover frames, chapters
deploy/               Dockerfile, compose, Caddy/nginx, systemd, deploy script
var/                  NOT in git: raw/ (originals), media/ (generated), data/ (SQLite), work/
```

## Requirements

- Go ≥ 1.27, Node ≥ 22 (npm), FFmpeg + ffprobe with libx264 and libwebp.
- No paid services. Google sign-in is optional; guests can browse and play everything.

## Local development

```sh
# 1. Build the Go binary
go build -o bal ./cmd/bal

# 2. Media: see "Media import" below (needs the Telegram downloads)

# 3. Run the API with local name-only sign-in (never enable on a public server)
BAL_DEV_LOGIN=1 ./bal serve --addr 127.0.0.1:8080

# 4. In another terminal, run the frontend with hot reload; it proxies /api, /auth and /media to :8080
cd web && npm install && npm run dev        # http://localhost:5173

# To test the production build instead: open http://localhost:8080
cd web && npm run build
```

To test on a phone over the LAN: run `./bal serve --addr 0.0.0.0:8080` and open `http://<laptop-ip>:8080`.

## Media import

The originals come from the channel's Telegram posts, downloaded in Telegram Web with the normal **Download** menu item. Telegram's public preview page doesn't serve these videos ("Media is too big"). `content/sources.json` lists, for every dance, the exact post of each video, scheme page and audio track, plus the filename Telegram gave it.

```sh
# Move downloads into var/raw/<slug>/<original filename> and record sha256 + status
./bal import --from ~/Downloads            # --copy to keep the files in Downloads

# Optional: contact sheet to choose a cover frame; then set "coverAt" in sources.json
./bal contact --every 6 vals-gavot         # → var/work/vals-gavot-contact.jpg

# Build web media for one dance or for all of them (outputs that already exist are reused; --force rebuilds)
./bal prepare vals-gavot
./bal prepare

# Inventory of what was obtained, what is link-only, and what is missing
./bal report > docs/assets.md
```

For each dance, `bal prepare` writes `var/media/<slug>/`:

| Output | How |
|---|---|
| `video-<sha12>[-e3].mp4` | Compatible H.264 sources at ≤ 6 Mbit/s with short keyframe gaps are **remuxed**. Other sources are encoded with libx264 CRF 22 at the same resolution and frame rate, with a keyframe interval of up to about two seconds for faster seeking. Both paths use `+faststart`. Transcodes use versioned URLs, and older files stay available to open players. |
| `poster.webp`, `poster-640.webp` | The real frame at `coverAt`, chosen by hand from a contact sheet. |
| `preview.mp4` | 8 s muted 480p loop from the cover frame (40–200 KB) for the hover preview in the catalog. |
| `thumbs/sprite-NN.webp` + `thumbs.vtt` | One frame every 2 s, 192×108 tiles in 8×8 sheets, WebVTT `#xywh` cues. |
| `schemes/<post>.jpg` + `-480.webp` | Copied untouched after a full decode check. |
| `audio/<post>.mp3` | Copied untouched after a full decode check. |
| `meta.json` | Catalog entry: version, paths, verified duration, source checksum. |

The version (the first 12 hex digits of the source's SHA-256) is stored with every note and resume position. If a tutorial is replaced, old notes show «к прошлой версии видео».

## Sign-in

Guests can watch everything. To keep notes, favourites, «Выучено», reactions and resume positions, people sign in with:

- **Email + password.** Registration signs you in at once; there is no confirmation email. Passwords are bcrypt-hashed, login takes the same time whether or not the email exists, and both endpoints are rate-limited per IP.
- **Google** (OpenID Connect with PKCE; the ID token is verified against Google's JWKS). In Google Cloud Console → Credentials, create an OAuth client of type *Web application* with redirect URI `https://<domain>/auth/google/callback`. Put the ID and secret in `BAL_GOOGLE_CLIENT_ID` / `BAL_GOOGLE_CLIENT_SECRET`.

Account linking follows nim: a Google sign-in with a verified email joins the existing account with that email. Because password sign-ups are unverified, any password on that account is removed and its sessions are revoked at that moment, so nobody can pre-register someone else's address and keep access.

## Deployment to the VPS

Production runs at **https://bal.aansl.com**: one Docker container behind the host's Caddy. Releases switch over without downtime (see below).

| Host path | Container | Contents |
|---|---|---|
| `/srv/bal/media` | `/data/media` (read-only) | prepared media, rsynced from the laptop (not in Git) |
| `/srv/bal/db` | `/data/db` | `bal.db` (SQLite WAL) + `secret.key` + `vapid.key` (push) + `pictures/` (copies of Google profile pictures) |
| `/srv/bal/bal.env` | env file | public URL, Google credentials (see `deploy/bal.env.example`) |

```sh
# Once on the VPS: create /srv/bal/bal.env from deploy/bal.env.example (chmod 600),
# append deploy/Caddyfile to /etc/caddy/Caddyfile and `systemctl reload caddy`.

# Every release, from the laptop (builds the image here, syncs media, switches over):
deploy/deploy.sh timeweb-ru
SKIP_MEDIA=1 deploy/deploy.sh timeweb-ru   # code-only release
```

**Zero-downtime releases.** Caddy proxies to two ports, `18090` and `18091` (`deploy/Caddyfile`). A release starts the new version in the free slot (`bal-blue` or `bal-green`), waits for `/healthz`, then stops the old one gracefully. Requests in flight finish, and anything that reaches a closed port is retried on the new one. If the new version never becomes healthy, it is removed and the old one keeps serving. The script refuses to run until Caddy's site block has both ports, so update it from `deploy/Caddyfile` and `systemctl reload caddy` once before the first release with this script. A reload doesn't drop connections. The first release replaces the old single `bal` container.

The image is built locally and streamed with `docker save | ssh docker load`, because the VPS has only 2 GB of RAM. Alternatives in `deploy/`: `compose.yaml`, `nginx.conf`, `bal.service` (systemd without Docker).

Telegram links use **https://go.bal.aansl.com**, configured with `BAL_SHARE_URL`. Install `deploy/share.Caddyfile` on the Caddy server for that host. It serves lightweight preview pages and poster images to link fetchers and forwards browser navigations to the main site with their query string intact. For a live check, paste a fresh `go.bal.aansl.com` link into Telegram's composer and confirm the card appears.

**Visit counting (optional).** Set `BAL_ANALYTICS_URL` (the Umami origin, e.g. `https://stats.coffer.rest`) and `BAL_ANALYTICS_SITE_ID` (the website's ID in Umami) in `/srv/bal/bal.env`. With either empty, counting is off and nothing is sent. Pages send small reports to `/api/pulse` on this site. The server checks them against a fixed list of pages and events (`internal/server/analytics.go`) and forwards them to Umami's `/api/send` in the background. No Umami script is loaded and the security policy stays `'self'`. Do Not Track and Global Privacy Control turn counting off in the browser.

**Playback monitoring.** In Umami's Events and Event Data reports, use `video-startup` and `video-seek` for milliseconds from play or seek to a new frame. The `frame` field is `presented` for compositor measurements and `ready` for the media-event fallback. `video-failure` records the playback phase and whether an error or timeout occurred. `video-session` records stall count and total stall milliseconds for the main player, including sessions with zero stalls. Use the dance page, browser and device filters when comparing samples. Timestamp links and timestamps in comments are counted by `timestamp-opened` and `comment-timestamp`.

**Mobile preview pilot.** After the Вальс-гавот preview plays for a second, eligible touch browsers with an active service worker are split between control and media warming. Both groups warm the player bundle. The treatment downloads up to 512 KiB of the current MP4 once per page session, with a 30-second reuse window. Data Saver and reported 3G-or-slower connections skip the media request. Compare `video-open` (tap to frame, grouped by `group`) and use `video-warm` to count completed warm-up downloads. Openings that never reach a frame have no timing sample.

Uptime Kuma checks the homepage, the catalog response at `/api/catalog`, and a small byte range inside the live `vals-gavot` MP4. Update the range monitor URL when that encode is replaced. The Timeweb VPS collects network throughput every minute with `sysstat-collect.timer` (`OnCalendar=*:00/1`). Run `ssh timeweb-ru 'LC_ALL=C sar -n DEV --iface=eth0'` and read `txkB/s` for outgoing traffic. Use the provider's confirmed port limit to set a saturation threshold.

**Push notifications.** Signed-in people can turn on «Уведомления» in the account menu or the bell's list. A reply, an @mention, or a dance whose video has just appeared on the site then reaches the device while the site is closed. The server sends them itself with Web Push (`internal/server/push.go`): no extra service, no keys to configure. Its VAPID key is created once in `/srv/bal/db/vapid.key`; keep that file, since a new key silently cuts off every device that turned notifications on. New videos are checked a minute after start-up and then every 5 minutes, and each dance is announced once. The first check only records what is already there. iPhones get notifications only in the installed app (iOS 16.4+), Android in Chrome, Brave or Yandex Browser.

**Google sign-in in production** needs `https://bal.aansl.com/auth/google/callback` added to the OAuth client's authorized redirect URIs in Google Cloud Console.

**Backups:** `sqlite3 /srv/bal/db/bal.db ".backup /srv/bal/db/backup-$(date +%F).db"`. Keep `var/raw` on the laptop; it holds the originals.

## Adaptive streaming (HLS)

Not added. Every tutorial is a single progressive MP4 of 24–111 MB at 1.4–5 Mbit/s. That's well below typical 4G throughput, and the browser seeks via Range requests. Add HLS only if real phones on the hall's network show stalls: measure with the browser's Network panel or Vidstack's `waiting` events.
